# AgentVille — Progression (sub-project 3)

**Status:** implemented (approved by the fork's owner on 2026-10-16, delegated: "do it alone and deliver it ready"); built by `docs/superpowers/plans/2026-10-16-office-progression.md`.
**Builds on:** sub-project 1 (the office) and sub-project 2 (situated behaviour).

## Goal

Turn the office into a light game layer about the user's own agents: agent types earn XP and level up, the office celebrates milestones with achievements, a team panel ranks who worked the most, the light follows the real time of day, and the office collects decoration as the team grows. Everything is local, free and private.

## Decisions

| # | Decision | Rationale |
|---|---|---|
| G1 | **Progress lives in one JSON file in the extension's global storage** (`globalStorageUri`), schema-versioned, one record per machine and editor, shared by every window of that editor (VS Code, Cursor and others each have their own global storage) and never synced or sent anywhere. A single window writes it (see *G1 storage*, amended by ruling R5). | Every window sees the same progress, and XP no longer depends on which windows are open or on last-writer-wins between them. |
| G2 | **XP comes only from data the provider already has**, so a closed office still costs nothing extra: 1 XP per minute an agent is `working` (credited on refresh ticks, each credit capped at 60 s so sleep or long gaps never inflate it), and +10 XP each time a subagent run completes (its id is counted once; the counted-id set is bounded to the latest 2000). Runs already finished when they come into view earn nothing: on the first tick after install, a reset or re-enabling (ruling R3), and in a session not seen on the previous tick, such as one continued after more than an hour out of view (ruling R10). | No new scanning, no transcript reads for XP. Tool-level counters would need the office open, so they are out. |
| G3 | **Agent type** (amended by ruling R9) = the launch's `subagent_type` (the Agent tool's input), else the `agentType` in the subagent's sidecar, else its display `name`; lowercased and trimmed. Top-level sessions are type `session`; background agents nested under a launcher are type `background agent`. | One type per kind of agent rather than per launch (a launch's `name` is often unique), so levels build up and *Team player* means five kinds of agents; stable across runs. |
| G4 | **Levels:** level n needs `25·n·(n−1)` XP (L2 = 50, L3 = 150, L5 = 500, L10 = 2250). Name tags show the type's level from level 2 (`explorer-agent · Lv 3`); level 1 shows no suffix (ruling R11). | A gentle curve: first levels in a day of work, later ones over weeks. |
| G5 | **Eight achievements**, each unlocked once and stamped with its time: *First hire* (first completed subagent run), *Team player* (5 distinct subagent types completed), *Full house* (6+ subagents working at once), *Night owl* (an agent working between 00:00 and 04:59 local), *Early bird* (an agent working between 05:00 and 06:59 local), *Marathon* (120 working minutes credited in one local day across all agents), *Century* (100 completed subagent runs), *Veteran* (any type reaches level 5). | Every condition is computable from G2's signals. |
| G6 | **Team panel** inside the office (a button in a corner): ranking of agent types by XP with level, XP to next level, completed runs and working time; the office XP and next decoration; the eight achievements, unlocked ones with their date. Unlocking an achievement while the office is open shows a small toast; unlocks that happen while it is closed are shown as toasts the next time it opens. No VS Code notifications. | Celebrates without interrupting work. |
| G7 | **Day/night follows the real local clock**, recomputed once a minute: day (07:00–17:00) unchanged; dusk (17:00–19:00) a warm tint rising; evening (19:00–21:00) turning blue; night (21:00–05:00) dark blue; dawn (05:00–07:00) fading back. At night the desk monitors glow softly. The tint is a pure function of the time, unit-tested. | Cheap (one overlay + a few light sprites) and readable. |
| G8 | **Unlockable decoration**: eight wall-mounted 16×16 CC0 items (e.g. clock, paintings, poster, whiteboard, window, trophy shelf) placed on wall tiles, unlocked in order as the **office XP** (sum of all types' XP) passes 100, 300, 600, 1000, 1500, 2200, 3000 and 4000. Wall-mounted only, so walkability and paths never change. | Visible progress without touching movement rules. |
| G9 | **Reset command** "AgentVille: Reset Office Progress" with a modal confirmation; a setting `agentville.progression.enabled` (default `true`) turns accrual and the game layer off. | User control. |
| G10 | **Boundaries stay**: XP rules, levels, achievements, lighting and decoration unlocks are pure modules with tests; the progress file store is VS Code glue (its lease and request decisions are pure and tested); the webview only renders a `progress` message. | Same discipline as sub-projects 1 and 2. |

### G1 storage (ruling R5)

`progress.json` holds `{ generation, state }` and is written only by the window holding `lease.json` (`{ holder, heartbeat }`: a random id per window and the epoch ms of its last renewal). On each live refresh tick a window reads the lease: it renews its own lease once the heartbeat is 10 s old, follows a fresh lease held by another window, and takes over a missing lease or one stale for more than 90 s. It claims the lease only when it can start from the progress file (see below), re-reads the file once the lease is its own (the 60 s credit cap keeps the gap from inflating XP), and deletes temp files older than 60 s left by a crashed write. Only the holder accrues, from every project's sessions within the last hour (no workspace filter), and only once the provider has finished its first load with monitoring on. It saves at most every 30 s, and only when progress (XP, runs, counted ids, achievements, toasts, generation or the paused flag) changed; per-tick bookkeeping rides along; a newly unlocked achievement is saved at once so other windows can toast it. On dispose it writes synchronously and deletes its lease so the next window takes over at once; a holder whose save fails deletes its lease too, rather than keep a heartbeat it cannot write under. Other windows never write `progress.json`: they re-read it on their own ticks once the holder has replaced it, and a reset or a toast acknowledgement from them becomes a one-shot `req-*.json` file the holder applies, saves, then deletes (a reset is stamped one above both the window's generation and the file's; acknowledgements apply only to the generation they saw). Every write goes through a temp file and a rename (retried once). While progression is disabled the holder pauses the clock (`lastTickAt = null`), so re-enabling seeds the counted runs instead of crediting the disabled period.

Unreadable files (rulings R7, R12): before replacing a valid `progress.json`, the holder copies it to `progress.json.bak`, and every reader (takeover, followers, the save-time generation check) falls back to that backup. A file that exists but is not a valid `{ generation, state }` doc (empty, partial, `{}`, `[]`) is invalid. Progress starts fresh only when both files are missing, or when both are invalid, in which case the holder keeps the main file as `progress.json.corrupt-<ms>`, logs it, and starts fresh. A file whose `state.version` is newer than the extension's is never migrated: that window claims no lease and keeps showing what it last read; an unreadable file (an I/O error) also leaves every window following.

## Protocol additions

- `ToWebview` gains `{ type: 'progress'; progress: ProgressView }`, sent on open (after `ready`), on every change, and not while hidden. `ProgressView` carries the ranking rows, office XP, unlocked decoration ids, achievements (id, title, description, unlockedAt?) and the list of achievements to toast now.
- `AgentView` gains `level?: number` for name tags.
- `ToExtension` gains `{ type: 'achievementsShown'; ids: string[] }`: toasts stay in `progress.toasts` until the office acknowledges them (ruling R6), so a toast is never lost to an office closed before showing it. Until the acknowledgement reaches the holder, the same id can arrive in several `progress` messages and the webview shows each id once. Two windows with the office open may both show a pending toast before one acknowledges it (accepted).

## Acceptance

1. Working agents and completed subagent runs earn XP as in G2; restarting VS Code keeps progress; the same run never counts twice.
2. Name tags show levels; the team panel ranks types correctly and shows achievements and the next decoration.
3. Each achievement unlocks exactly once under its condition and toasts once.
4. The light follows the local clock as in G7; monitors glow at night.
5. Decoration appears as office XP crosses each threshold and never blocks a path.
6. Reset clears everything after confirmation; disabling the setting stops accrual and hides the layer.
7. All pure modules unit-tested; gate green; `.vsix` stays under 2 MB with only CC0 art added.
